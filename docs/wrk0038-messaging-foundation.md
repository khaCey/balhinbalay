# WRK0038 persistent messaging foundation

Reviewed base: WRK0037 commit `0e759cf63ba0c0583e57f405aa5982b6aea56ed4`, tree `b9587d1159c3c9faf90727117d18cecab18468a1`. Work branch `wrk0038-persistent-messaging-foundation`. Migration `005_marketplace_messaging.sql` adds conversations, immutable participants and immutable text messages after unchanged001–004. Entity UUIDv7 values and timestamps are server-generated; client UUIDs only identify retry requests.

The existing explicit same-origin marketplace proxy admits GET/POST conversations, GET conversation UUID, and GET/POST conversation UUID/messages. Ordinary verified active user sessions, proxy-key and canonical mutation Origin checks are reused directly. Sender membership and original recipient are server-derived; body/identity mass assignment is rejected. No admin thread access is added. Responses include only safe title/type/listing UUID context, opaque participant IDs/roles, generic sender labels and text, never private listing aggregates or contact fields. Client-authored text is rendered as text, not HTML.

Creation atomically inserts one thread, exactly its two distinct original participants and the first message. Unique listing/initiator/original recipient plus capability→conversation locks serialize races. Unique participant/request UUID makes repeated sends replay their committed result; changed text conflicts. Already-committed retries insert nothing even when frozen. Deferred constraints enforce participant count/mapping; composite sender FK rejects cross-thread attribution; participants/context/history cannot be silently reassigned or deleted.

Reads require participant membership. Existing threads remain replyable after unlisting/sale/rental/closure. Sending locks the original recipient's lister_access row, requires active, then locks the thread. Existing capability administration uses compatible locks. Suspended/revoked/pending/missing capability freezes both senders without changing timestamps; active restoration restores sends. Requester account/session eligibility is always enforced. Deleted/anonymised participant labels become `Deleted user`; RESTRICT history FKs integrate with the reviewed guarded admin deletion. No anonymisation execution, retention duration or purge policy is implemented.

Pagination uses bounded1–100 pages and database-precision `(created_at,id)` cursors. Messages are returned chronological within each latest/earlier page. Inbox ordering uses immutable creation time/UUID, so sends do not move a pagination cursor. Text is bounded to2000 characters/6000 UTF-8 bytes, within the existing8KiB proxy boundary. Request key reuse is scoped to the sending participant/thread.

## Feature and release boundaries

Historical WRK0038 checkpoint: auth-only deployments remain valid. Messaging requires the existing MARKETPLACE_ENABLED plus explicit MARKETPLACE_MESSAGING_ENABLED; startup refuses absent005 only when messaging is enabled. Neither flag runs migrations. **At WRK0038, production conversation initiation was unavailable**: POST start additionally required runtimeMode=test and explicit BB_MESSAGING_SYNTHETIC_START=true, with no production override. Sample cards/enquiry actions could not start real threads; UI provided authenticated inbox/thread/send. WRK0041 now supersedes only that initiation restriction after Coordinator-reviewed moderation/publication, requiring the same current genuine approved-active publication validator and preserving the existing thread contract. See wrk0041-real-listing-contact.md. No deployment or production migration is implied.

Only the non-server WRK0038 Actions workflow runs disposable Ubuntu/PostGIS16-3.4 integration. It creates and drops separate empty and account-only-upgrade synthetic databases. Synthetic approved-active listings are inserted only in that test file; no approval/publication API, production fixtures or demo migration exists. CI covers existing auth/listing regressions, real migration/deferred constraints, privacy/IDOR, initial and send races, lifecycle/freeze/restoration, database lock observation and history protection. No deployment workflow is changed. No runtime/production migration/public access/WRK0019 work is authorised by this source.

Messages and `/chat/<UUID>` use server reads/sends, explicit empty/error/loading/frozen states and retry keys held only in React state. Numeric demo chats are rejected; older persisted demo messages remain discarded. No unread/read-receipt claim, notification, fake reply, direct-contact reveal or storage-backed demo is restored.
